# marimo vs Jupyter: реактивный и нереактивный ноутбук

## Модель выполнения

| Аспект | Jupyter | marimo |
| --- | --- | --- |
| Единица | ячейка, выполняется по клику, в любом порядке | ячейка = узел графа, выполняется когда меняются её входы |
| Состояние | глобальное, «скрытое»: переменная живёт после удаления ячейки | выводится из графа; удалил ячейку — исчезли её переменные |
| Порядок | порядок в файле не равен порядку выполнения | порядок выполнения = топологическая сортировка DAG по переменным |
| Повторное имя | можно переопределять переменную в разных ячейках | запрещено: одна переменная определяется ровно в одной ячейке |
| Формат файла | `.ipynb` — JSON с выводами, плохо диффится | `.py` — обычный Python, ячейки = функции с декоратором `@app.cell` |
| Воспроизводимость | не гарантирована (зависит от истории кликов) | гарантирована: файл можно запустить как скрипт `python nb.py` |
| Интерактив | виджеты через ipywidgets, состояние вне графа | UI-элементы — часть графа; изменение слайдера перезапускает зависимые ячейки |

## Что это значит для «ячейка = задача»

**Jupyter (нереактивный).** Ячейка — журнал действий. Подходит для исследования, где
человек сам решает, что и когда запускать. Для системы задач это минус: нет способа
понять, что устарело после правки другой ячейки. Метаданные можно хранить в
`cell.metadata`, но их никто не исполняет.

**marimo (реактивный).** Ячейка — функция с явными входами и выходами. Это уже почти
задача: зависимости выводятся из кода, а не из порядка. Если задача A даёт `config`,
а задача B его использует, то правка A автоматически инвалидирует B. Для деплоя как
источника правды это ключевое свойство: состояние всегда согласовано с кодом.

## Где marimo ограничивает

- Одна переменная — одна ячейка. Итеративные «перезапиши `df`» сценарии не работают.
- Нет произвольного порядка: нельзя «просто выполнить эту ячейку» без пересчёта зависимых
  (можно включить lazy-режим, тогда зависимые помечаются устаревшими, а не пересчитываются).
- Побочные эффекты (запись файла, `ssh`, `docker`) не видны графу. Их надо оборачивать
  так, чтобы результат возвращался как переменная, иначе реактивность ломается.

## Вывод для notch

Берём marimo как исполняемую основу: DAG по переменным даёт бесплатную систему
зависимостей между задачами. Поверх него — свой слой метаданных задачи (статус,
приоритет, комментарии, кто исполнитель: человек или агент), который хранится
в самом файле рядом с ячейкой. Побочные эффекты (деплой) моделируем как задачи,
возвращающие результат-артефакт, чтобы граф видел их.
